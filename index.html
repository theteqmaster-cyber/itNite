The Level 1 Data Flow Diagram (DFD) maps the functional boundaries of the Smart Livestock Monitoring System. It describes the routing of data from collar sensors through processing engines to administrative and user actors, supported by persistent storage.

Figure 1: Level 1 Data Flow Diagram for Smart Livestock Monitoring System

Data Flow Entities & Operations

The system isolates user operations from direct hardware telemetry. Process 1.0 (Manage Records) acts as the central administrative system for setting up entities. Process 2.0 (Monitor Livestock) constantly processes incoming GPS streams from devices, maps coordinates relative to bounding zones pulled from D2, and streams current locations to the farmer. Process 3.0 (Generate Alerts) acts on violations or flatlines, updating D5 and notifying farmers immediately. Process 4.0 (Analyze Historical Data) aggregates geographic telemetry patterns for long-term reporting.

Relationship Design Justifications

  • Inheritance (Generalization): Farmer and SystemAdmin extend the abstract User class, reusing profile authentication capabilities.
  • Aggregation: Farmer holds a collection of Livestock records. Livestock can exist independent of a single farmer registry (e.g. transfer between cooperative members).
  • 1:1 Composition/Association: Each Livestock animal is associated with exactly one tracking Device collar at any instance.
  • 1:M Associations: A tracking Device records sequential SensorData historical records. A Livestock animal generates multiple transactional Alert reports.

The following Java classes represent the physical implementation of the core domain layer modeled in the UML design: Device, Livestock, and Farmer.

3.1 Device Class

package com.iot.livestock; import java.util.Date; public class Device { private String deviceId; private int batteryLevel; private String status; // Constructor public Device(String deviceId) { this.deviceId = deviceId; this.batteryLevel = 100; this.status = "ACTIVE"; } // Method 1: Transmit data to the central system public SensorData transmitData(double latitude, double longitude) { if (this.batteryLevel < 5) { this.status = "LOW_POWER"; } return new SensorData(String.valueOf(System.currentTimeMillis()), latitude, longitude); } // Method 2: Update battery status from sensor reporting public void updateBattery(int newBatteryLevel) { this.batteryLevel = Math.max(0, Math.min(100, newBatteryLevel)); if (this.batteryLevel == 0) { this.status = "OFFLINE"; } } // Getters public String getDeviceId() { return deviceId; } public int getBatteryLevel() { return batteryLevel; } public String getStatus() { return status; } }

3.2 Livestock Class

package com.iot.livestock; public class Livestock { private String livestockId; private String species; private int age; private String status; private Device trackingDevice; // Constructor public Livestock(String livestockId, String species, int age) { this.livestockId = livestockId; this.species = species; this.age = age; this.status = "NORMAL"; } // Method 1: Assign an IoT device collar public void assignDevice(Device device) { this.trackingDevice = device; } // Method 2: Evaluate physical coordinates against a boundary public boolean checkGeofence(double lat, double lng) { // Simulated bounding coordinates: Latitude [-20.1, -20.2], Longitude [28.5, 28.6] if (lat < -20.2 || lat > -20.1 || lng < 28.5 || lng > 28.6) { this.status = "STRAYING"; return false; // Breached Geofence } this.status = "NORMAL"; return true; } // Getters and Setters public String getLivestockId() { return livestockId; } public String getStatus() { return status; } public void setStatus(String status) { this.status = status; } }

4. Database Design (ERD)

Hover over table entities to isolate their primary-to-foreign key relationships.

The database design provides a 3rd Normal Form schema layout mapping farmers, their livestock, associated collar tracking devices, the historical telemetry, and generated system alert events.

Figure 3: Entity Relationship Diagram (ERD) with Crow's Foot Notation

Database Entity Profiles & Constraints

Entity (Table) Relationship (Cardinality) Target Entity Primary Key Foreign Key & Constraints
FARMERS 1 : Many LIVESTOCK farmer_id None
LIVESTOCK Many : 1 FARMERS livestock_id farmer_id references FARMERS
DEVICES 1 : 1 LIVESTOCK device_id livestock_id references LIVESTOCK [UNIQUE]
SENSOR_DATA Many : 1 DEVICES data_id device_id references DEVICES
ALERTS Many : 1 LIVESTOCK alert_id livestock_id references LIVESTOCK

Normalization & Integrity Rules

  • Referential Integrity: Foreign keys are strict mappings. Deleting a farmer cascade-deletes owning livestock entries. Disassociating a device clears its livestock_id relationship reference.
  • Unique Constraint [1:1]: The livestock_id column in DEVICES is set to UNIQUE, restricting a tracker to a single animal at any time.
